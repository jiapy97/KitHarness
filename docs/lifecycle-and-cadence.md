# 生命周期容量与触发频率

本页对应第 7 步。保留反思者、整理者、确定性执行器和生命周期退役机制。

## 哪些技能会参与容量管理

生命周期仍在主会话 SessionStart 检查，按项目层和全局层分别处理，只管理插件自己创建的技能。

| 技能状态 | 处理规则 |
| --- | --- |
| 仍在观察期 | 保留，参与召回，不计入成熟技能容量 |
| 已成熟，从未调用也从未查看 | 毕业审核归档；暂停审核时进入容量竞争 |
| 已成熟，被查看过但没调用 | 保留毕业资格，以零使用率参与容量竞争 |
| 已成熟，有调用记录 | 以调用次数 / 创建后所在层的请求数参与容量竞争 |

先处理毕业审核拒绝的技能，再对所有剩余成熟技能执行容量限制。
超出容量时，优先归档使用率最低的；使用率相同按技能名称的稳定哈希决定，目录遍历顺序不影响结果。
`view` 只说明技能被查看过，不增加使用率。暂停毕业审核也不会让零调用技能绕过容量限制。

修复前，“只看过”或“因暂停审核而保留”的零调用技能都直接跳过容量池，成熟技能可能超过配置上限。
修复后，它们进入同一个容量池。观察期、用户/原生技能及禁用的全局层仍遵守原有规则。
归档移动完整目录，保留附件和元数据，可以用现有 restore 操作恢复；没有新增物理删除。
恢复后的技能若仍处于容量压力下，后续生命周期检查仍可能再次归档。

## 学习频率按什么计数

| 用途 | 单位 | 范围与触发点 |
| --- | --- | --- |
| 反思 | 有合法 session ID 的主会话工具调用 | 会话内累积；Stop 判断，SessionEnd 尝试处理尾部 |
| 整理 | 同一批主会话工具调用 | 项目内跨会话累积；Stop 判断 |
| 生命周期观察期及使用率分母 | 主会话 Stop，即对话轮数 | 项目/全局层分别累积；保持已有语义 |

反思默认每 50 次工具调用，整理默认每 250 次。纯聊天轮次不会触发这两类学习；插件子会话的工具和 Stop 不计入它们。
整理频率设为 `KITHARNESS_CONSOLIDATE_EVERY_N=0` 时暂停整理，活动计数仍累积；重新启用后最多发起一次处理已累计周期。
负值或非数字会提示并回退到默认值。

整理使用独立的项目工具总数和已领取进度，不受反思计数清零、SessionEnd 清理或会话切换影响。
一次 Stop 跨过多个周期时，只发起一个整库整理，不补发多份重复任务；未满一个周期的余量留下。
例如周期为 250：总数从 240 跳到 760 时只发起一次，领取到 750，留下 10 次给下个周期。
并发 Stop 用文件锁领取进度，避免相同活动重复触发。进度仅在同步启动返回成功后保存；启动抛错或返回错误时保留进度，下一次 Stop 可以重试。
每次启动使用独立 run ID，避免重试覆盖上一次的队列或运行记录。
启动与进度保存不是一个事务；若中间发生崩溃或磁盘错误，后续可能再次请求整理，仍受后台限额约束。已发起整理但保存进度失败时，也保留反思计数，不在同一 Stop 追加反思任务。

反思与整理同时到期时，优先发起整理，并保留反思计数。后续 Stop 或 SessionEnd 仍可触发反思，避免同一次 Stop 主动发起两个任务争抢默认的一个项目并发名额。
这是启动优先级，不是等待执行的队列：实际后台任务仍受[第六步的限额](runtime-controls.md)约束。
启动后被并发限制跳过、运行失败、宿主退出等情况，不保证自动补跑；本步没有增加调度服务或付费模型调用。

升级时，原来的 `requests` 是对话轮数，不会当作工具次数迁移。新工具总数从首次记录开始积累，已有 sidecar、版本、回执和归档不需要迁移。
新计数保存在项目配置根目录的 `kitharness/tool-calls` 和 `kitharness/curator-watermark`；它们是运行状态，不应手工改写成旧请求数。

## 验证范围

回归用例覆盖零调用容量竞争、暂停审核、观察期、稳定排序、完整归档恢复及项目/全局隔离。
触发用例覆盖纯聊天、重操作跨周期、余量、跨会话、反思让位、启动失败重试，以及真实并发 hook 进程的计数和领取行为。
测试使用临时技能目录和假启动器，不能据此宣称真实模型的整理质量或效果已有提升。
